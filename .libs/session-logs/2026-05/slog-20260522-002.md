## SLOG-20260522-002.概要 — 概要

SLOG-20260522-001 で「v1.5.2 が出たら yokemo は `install.py --update` で取り込める」と案内したが、yokemo プル子から「install.py --update は .nxt-core/ を再取得しない設計で、本元の修正がプル子に届く経路が存在しない」という指摘が来た。実装を確認した結果、指摘は完全に正しく、giget 配布の根本的なギャップが判明。新規スクリプト `update.py` を追加してこの空白を埋め、v1.6.0 として配信した。

## SLOG-20260522-002.作業内容 — 作業内容

### 1. 指摘の検証

- `core/install.py:main()` (775-833 行) を Read → CLAUDE.md / Hook / permission / variant / `.claude/skills/` / マニフェスト / ディレクトリ / `.gitignore` / `.libs/research/` clone / QA 設定までを管理するが、**`.nxt-core/` 自体は一切触らない** ことを確認
- `bootstrap.py` を Read → giget で `.nxt-core/` を取得するが新規初期化専用で `--update` モードは無し。既存プロジェクトで再実行すると starter テンプレートまでプロジェクトルートに上書きされる
- 結論: 本元での修正をプル子に届ける経路が無い (= 過去のリリース全てが配布手段なしの状態だった)

### 2. 方針の選択 (3 案 → 案 B 採用)

- **案 A** install.py --update を改修して内部で giget を呼ぶ — 自分自身を上書きする難しさで複雑化
- **案 B (採用)** 新規スクリプト update.py を追加 — bootstrap.py 並列のスタンドアロン、`.nxt-core-new-<ts>/` に取得 → atomic rename で切替
- **案 C** 当面マニュアル運用 — エル子側の修正なし

### 3. update.py の実装

- 本元直下に `update.py` を新規作成。標準ライブラリのみ + `npx giget` 子プロセス呼出 (bootstrap.py と同じスタンドアロン設計)
- フロー: giget で `.nxt-core-new-<ts>/` に取得 → sanity check (`core/paths.py` / `core/install.py` / `core/constants.py` / `VERSION` の存在) → `.nxt-core/` を `.nxt-core-old-<ts>/` にリネーム → 新版を `.nxt-core/` にリネーム → `install.py --update` 子プロセス呼出 → 成功で old を削除 / 失敗で rollback
- 本元保護: 冒頭で `.nxt-core/` が無ければ即 `sys.exit(1)` (本元には `.nxt-core/` が存在しないため意図しない実行を防ぐ)
- Auto Mode classifier がローカル実取得テストをブロックしたので構文チェックのみで合格

### 4. bootstrap.py / specs の更新

- `bootstrap.py:DIST_FILES` に `"update.py"` を追加 → ローカルソース経由の `copy_nxt_core` でも `.nxt-core/update.py` として配布される
- `specs/03-tools.md` に `update.py` の節 (3 つの設計意図 + フロー 6 ステップ) と依存関係セクションを追加

### 5. リリース

- `bash release.sh v1.6.0` で VERSION bump + 検証 + commit + tag + push + GitHub Release まで完走

## SLOG-20260522-002.決定事項 — 決定事項

- **設計ギャップへの対処は案 B (新規 update.py 追加)** — install.py を改修する案 A は「自分自身の上書き」の複雑さがあり、マニュアル運用の案 C は毎回ユーザー手作業になる。bootstrap.py 並列のスタンドアロンスクリプトを追加するのが最も clean
- **update.py は標準ライブラリのみ + npx giget 子プロセス呼出** — bootstrap.py と同じ設計を踏襲。`core/` 内の関数を import すると giget 実行中に `.nxt-core/` を rename したときにファイルロックが起こりうるため
- **atomic rename + rollback 機構を実装** — giget 失敗 / sanity check 失敗 / rename 失敗 / install.py 失敗の 4 つの失敗パスそれぞれで残骸を適切に片付け、`.nxt-core-old-<ts>/` は install.py 失敗時のみユーザー判断用に残す
- **本元保護は `.nxt-core/` 不在チェックで実装** — 本元には `.nxt-core/` が無いため、誤って本元で `python update.py` を実行しても即エラー終了する (`IS_SOURCE` の検出は core/ 依存になるため避けた)
- **バージョンは v1.6.0 (minor bump)** — 新規エントリポイントの追加で新ユーザーインターフェースが増えるため、SemVer 的に minor が妥当。v1.5.3 (patch) ではなく v1.6.0 を選択
- **既存プル子への移行は 1 回だけ手動ワークアラウンド** — yokemo を含む既存プル子は v1.5.2 / v1.5.1 で update.py を持たないため、初回だけ `rm -rf .nxt-core && npx giget gh:... .nxt-core && python .nxt-core/core/install.py --update` を実行してもらう。v1.6.0 以降は `python .nxt-core/update.py` 一発
